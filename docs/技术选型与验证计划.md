# 本机防火墙工具：技术选型与验证计划

日期：2026-11-11

依据：《本机防火墙工具—首版规格》以及本轮补充约束：**暂时不考虑 Apple Developer Program 账号**。

## 1. 推荐结论

当前推荐组合为：**Tauri 2 + React/TypeScript + Rust + SQLite；Windows 使用 WFP；macOS 使用 PF，并配套精确状态清理和 PF 日志采集模块。**

可以先确定界面、共享规则核心、存储和 Windows 的主要方向。macOS 的 PF 路线作为首选原型方案，只有通过精确撤权、真实日志和规则共存测试后，才冻结为首版交付方案。源码中存在接口，不等于已证明所有目标系统都能可靠工作。

继续保留全部核心要求：本机管理、单个 IP 与 CIDR、TCP/UDP、白名单外拒绝、撤销已有通信权限、操作日志和网络访问日志。远程管理不纳入当前实现。

### 技术组成

| 部分 | 选择 | 作用与状态 |
| --- | --- | --- |
| 桌面容器 | Tauri 2 | 统一 Windows/macOS 窗口、托盘和本地命令入口；建议采用 |
| 界面 | React + TypeScript + Vite | 规则列表、编辑表单、日志筛选和状态展示；建议采用 |
| 共享核心 | Rust | IP/CIDR 规范化、规则验证、策略版本、日志模型、错误处理；建议采用 |
| 常驻服务 | Rust 独立进程 | 与界面生命周期分离，负责受授权的规则管理和日志落盘；建议采用 |
| Windows 执行层 | WFP 用户态管理 API，配合必要的 Windows Firewall 精确放行规则 | 通过系统过滤引擎执行；原型阶段验证仲裁、撤权和事件采集 |
| macOS 执行层 | PF anchor/table + 小型 C ABI 适配层 | PF 规则管理和指定地址、协议、端口的状态清理；必须先通过原型 |
| 网络日志 | Windows WFP Net Events；macOS pflog + libpcap | 读取系统过滤事件，不能用普通抓包结果冒充允许/拦截结果 |
| 本地存储 | SQLite，Rust 侧使用 rusqlite | 服务进程统一写入配置、规则版本与日志；建议采用 |
| 本地通信 | Windows Named Pipe；macOS Unix Domain Socket | 有权限检查的本机通信，无需开启 HTTP 管理端口 |
| 后台启动 | Windows Service；macOS LaunchDaemon | 支持界面关闭后的运行及重启恢复；安装和恢复行为需验收 |
| 内部打包 | Windows NSIS 安装程序；macOS 内部测试安装包 | 包含后台服务安装、升级、卸载流程；与普通 Tauri 窗口打包分别验证 |

这里只确定技术系列。创建项目时选择当时的稳定版本，提交 Cargo.lock 和前端锁文件，并固定 Rust 工具链；不在缺少验证时指定“最新版本”的精确版本号。

## 2. 为什么选择 Tauri

这个产品的主要界面是表单、规则列表和日志，不需要复杂的图形渲染。真正的工作量在两个操作系统的网络过滤和后台权限管理。

**Tauri 适合本项目的原因：**

- Rust 后端可直接复用规则核心和平台适配逻辑。
- 使用系统 WebView：Windows 使用 WebView2，macOS 使用 WKWebView。安装时需要处理 Windows WebView2 依赖，界面需要在两个引擎上验证。[1][2]
- 能提供跨平台窗口、托盘和安装包基础能力。[1][3]
- 界面保持普通用户权限；需要系统权限的行为放在独立后台服务中。Tauri 的进程隔离不能替代服务端授权检查。

### 框架比较

| 候选 | 优点 | 本项目的代价 | 结论 |
| --- | --- | --- | --- |
| Tauri 2 + React | Rust 集成直接；Web UI 开发方便；使用系统 WebView | 要处理 WebView 差异、原生安装和服务生命周期 | 首选 |
| Electron + React | Chromium 渲染环境统一；Node.js 生态成熟 | 仍然需要原生服务；引入 Chromium/Node 运行环境，资源成本需另行测量 | 团队已有大量 Electron 代码时可重新考虑 |
| 两套原生 UI：WinUI 与 SwiftUI/AppKit | 平台体验和系统集成直接 | 界面、状态管理、打包测试需要维护两套实现 | 对当前内部试用规模投入偏大 |
| Wails / Flutter / Avalonia | 都能承担桌面界面 | 无法省去 WFP/PF、权限服务与平台验证；当前没有既有 Go/Dart/.NET 技术资产要求 | 不作为首选，团队背景变化时可重评 |

Electron 的主进程/渲染进程模型见官方文档。[4] 本次没有做各框架的内存、包大小或启动时间基准测试，因此不提供虚构的性能数字。

## 3. Windows：选择 WFP，避免把普通规则顺序当作防火墙逻辑

### 3.1 规则优先级

普通 Windows Firewall 规则中，**显式拒绝优先于冲突的允许规则**，也不支持管理员任意指定规则权重。[5] 因此不能简单建立“拒绝所有来源访问 8080”和“允许 A 访问 8080”，期待后一条自动成为例外。

建议使用 Rust 的 Windows API 绑定调用 WFP 用户态管理 API，在本软件拥有的 provider/sublayer 中编译策略。原型先使用独立 sublayer 内的规则权重区分白名单放行与端口默认拒绝。

WFP 的 sublayer 之间还有软/硬许可等仲裁规则。自己的高权重不等于能任意覆盖其他安全产品；普通显式放行、显式拒绝、hard permit 和企业策略都要实测。[6]

另外，WFP 中允许某流量，不代表 Windows Firewall 的默认拒绝已经被解除。必要时通过 Windows Firewall 的受支持接口创建**仅属于本软件、限定端口/协议/来源的放行规则**，与 WFP 的限制规则配合；遇到其他明确拒绝策略时报告冲突，不关闭系统防火墙，也不修改全局默认策略。

WFP 更新与 Windows Firewall 规则更新不是同一项系统事务，需要自己的版本记录、执行步骤和恢复流程。

### 3.2 已有通信撤权

优先验证 `FWPM_LAYER_ALE_AUTH_RECV_ACCEPT_V4/V6`。Microsoft 明确说明：在相应 ALE 层增加或删除过滤器会触发策略变化，受影响 flow 的下一份数据触发重新授权；重新授权还可能由反向数据触发，文档专门提到单向 UDP 流的场景。[7]

这是实现“已有连接也不能继续传输”的依据，但仍需要验证 TCP 下载、WebSocket、双向 UDP、握手后单向 UDP，以及先有连接后启用规则的情况。

原型优先使用用户态 WFP 管理 API，暂不引入自研内核 callout 驱动。如果仲裁或覆盖范围的测试失败，应重新评估执行层，不能把用户态方案标为已经满足需求。

### 3.3 真实日志

- 使用 `FwpmNetEventSubscribe1` 或兼容的版本封装订阅事件。该接口在 Windows 8 及以后可用。[8]
- 核实 `CLASSIFY_ALLOW` 和 `CLASSIFY_DROP` 的实际来源、字段和覆盖范围；开启需要的采集选项。较旧的 WFP Logging 总览没有列出所有后续加入的事件，不应只凭该总览判定“不支持允许日志”。现代枚举包含允许和拒绝事件，SDK 头文件包含 `FWPM_NET_EVENT_KEYWORD_CLASSIFY_ALLOW`。[9][10]
- 回调进入有界队列，由独立写入任务批量保存到 SQLite。
- WFP 事件采集设置影响整个系统。读取原值，合并所需选项，避免卸载或停止时关闭其他软件仍在使用的采集。[11]
- 只将受管端口相关事件提供给本产品；区分本软件规则导致的拒绝和其他策略导致的拒绝。

## 4. macOS：当前采用 PF 原型路线

### 4.1 为什么本轮没有选 Network Extension

从受支持的平台 API 看，`NEFilterDataProvider` 是值得优先考虑的长期方向。它有 `update(_:using:for:)` 接口，可以在过滤回调之外更新已有 flow 的裁决，且在 macOS 10.15.4 起可用。[12]

但 Apple 的部署说明要求 macOS content filter 使用 System Extension；直接分发走 Developer ID 签名路径，且需要相应 Network Extension 配置与系统授权。[13] 用户目前不考虑开发者账号，因此不将这一条作为首版安装测试的依赖。

未来若具备签名条件，可以增加 Swift Network Extension 适配器。替换执行层不应要求重写界面、规则数据结构和日志查询。

### 4.2 PF 规则隔离

本软件使用独立命名的 anchor 和地址 table，只操作自己拥有的配置。

**关键细节：只给某个 anchor 加载规则，不代表主规则集会执行它。** 必须确保主规则集存在正确的挂载引用，并验证它相对其他 `quick` 规则的位置。安装和卸载要分别处理引用与内容，不能直接覆盖整个 `/etc/pf.conf` 或清空系统动态规则。[14]

使用 table 表达白名单，规则按本机端口、协议和地址族生成。IPv4 与 IPv6 都纳入匹配；没有列入白名单的另一地址族不能成为绕过路径。

原型需验证启用 PF 时现有系统 anchor 的行为，记录和管理自己的 enable reference。全局 PF 开关、状态表与其他服务共用，不把它们当作本软件独占资源。[14]

### 4.3 精确状态清理：需要小型原生模块

本机 `pf.conf(5)` 明确说明：命中已有状态的包会跳过规则重新评估。仅替换 table 或规则，无法证明撤权已经生效。[14]

本机 `pfctl -h` 和 `pfctl(8)` 提供的 `-k` 参数是 host/network，不能用按主机清理全部状态的办法冒充按端口撤权；那可能中断同一来源对其他端口的访问。

Apple 公开的 XNU 源码提供了更精确的依据：

- `pfioc_state_kill` 包含地址族、协议、来源、目标和传输层匹配信息。[15]
- `DIOCKILLSTATES` 的内核处理会检查来源/目标地址，以及两端的传输层字段。[16]
- 本次同时检查了 `xnu-8792.61.2` 标签下的相关结构与当前 main 分支，所检查的两个结构声明一致；这不能代替各系统版本的 ABI 验证。[17]

建议把此部分封装为**小型 C 适配层，由 Rust 后台调用**。对外只暴露经过校验的“对这些地址、协议和端口清理状态”请求，不暴露任意 ioctl 或任意命令执行。

该接口所需 PF 结构并未出现在本机公开 SDK 的对应头文件路径中；不能把公开内核源码误认为稳定 SDK 承诺。需要固定采用的结构定义、核对布局与 ioctl 编号、按系统版本验证，遇到未确认的 ABI 明确报不支持。

策略更新过程还需要考虑：先启用阻断再清理状态；清理后反向数据能否重新建立状态；TCP 双向传输和单向 UDP 是否都停止；同一来源在未配置端口上的连接是否持续正常。这些是 PF 原型的硬门槛。

### 4.4 PF 日志

使用 PF 的 `log` 规则配合 pflog 接口，通过系统 libpcap 采集。Apple 源码中的日志头包含 action、reason、规则号、anchor 信息，可以用于区分系统实际执行的放行和拒绝。[18]

普通网卡抓包只能证明“看见一个包”，无法直接证明“防火墙允许/拒绝了它”，因此不作为替代数据源。

原型必须确认：

1. 目标系统可创建和读取所需的 pflog 接口；本次仅枚举了现有设备，没有创建接口或抓取流量。
2. 配置 `log` 后，白名单放行和默认拒绝都能形成可解析事件。
3. 根据 anchor、规则映射及策略版本归属事件，避免规则更新后使用错误的规则编号映射。
4. 默认状态日志与逐包日志的频率不同，需要定义为“连接/访问尝试日志”，并对重复拒绝进行汇总。
5. 读取、队列或数据库丢失事件时显示缺口，不能用空列表表示“没有访问”。

日志的“允许”表示对应过滤层允许，不能保证应用服务响应成功，也不能证明 macOS Application Firewall 或其他安全软件没有继续拒绝。

### 4.5 无开发者账号的安装边界

PF 后台进程不依赖 Network Extension entitlement。内部测试可以采用管理员授权安装的 LaunchDaemon 和本机/ad-hoc 签名构建，但安装包未经 Developer ID 签名和公证时，可能需要人工处理系统信任提示；它不是正式对外分发体验。

不采用关闭 SIP、关闭 Gatekeeper 或修改整机安全策略作为试用条件。首轮安装验证应包含：合法的人工授权路径、服务启动、普通界面与服务通信、升级和卸载。

## 5. 进程、权限和数据边界

### 界面进程

- React 运行在 Tauri WebView 内，Tauri Rust 层负责本地类型化命令和 IPC。
- 展示规则、执行结果、过滤层状态、冲突原因与日志。
- 窗口关闭不退出独立后台服务。

### 后台服务

- Windows 使用 Windows Service，macOS 使用 LaunchDaemon。
- 校验每个请求的调用者和管理员授权，不把“来自本机”当作已经授权。
- 只接受规则模型和有限管理动作，不接受 shell 文本、任意可执行文件路径或任意系统 API 参数。
- 后台重新验证 IP/CIDR、端口、协议及规则版本，不能只依赖前端校验。
- 安装后的服务文件、配置和 IPC 端点采用系统权限保护；Windows Named Pipe 设置访问控制，macOS Unix socket 校验对端身份。

### 存储和策略提交

- SQLite 由后台统一写入，界面通过服务查询，避免界面直接修改“已生效规则”。
- 保存目标配置、应用中的版本、最后确认生效的版本和失败原因。
- 系统过滤规则变更与 SQLite 事务不能组成一个跨系统原子事务；采用准备、应用、核验、提交及失败恢复流程。
- 规则持久化与访问日志的写入策略分开：配置需要可靠提交，日志使用批量写入、轮转和容量上限。
- 管理操作日志与网络事件分表，索引优先覆盖时间、来源 IP、目标端口、结果；首版不引入搜索服务器。

## 6. 原型先后顺序与通过条件

**先验证 macOS 的 PF 能力，再接入完整界面。** 当前约束下，Mac 的精确状态清理和日志是选型最不确定的部分。

### P0：Mac 技术门槛

- 本机 8080/TCP 和独立 UDP 测试服务的白名单正常。
- 同一来源同时连接 8080 和另一个未配置端口；撤销 8080 权限后，前者停止传输，后者继续正常。
- 对单向 UDP、大文件下载、WebSocket，以及先建立连接再启用限制分别验证。
- pflog 能输出真实允许和拒绝事件，日志归属准确。
- 与现有规则、已有状态共存，不全量清空规则或状态；可以正确撤除本软件配置。
- 验证无开发者账号条件下的正常安装与服务授权流程。

通过条件：上述行为均有实机记录；失败时继续调整 PF 适配，不自动删掉“已有连接撤权”或“网络日志”需求。

### P1：Windows 技术门槛

- WFP 规则与 Windows Firewall 默认策略、已有显式放行/拒绝规则共存。
- ALE 策略变化能阻断已有双向 TCP 与单向 UDP 通信。
- 能区分实际允许和拒绝事件，而非根据当前配置推测结果。
- 策略更新失败、服务异常和重启恢复行为可解释、可验证。

### P2：共享核心、界面和内部安装包

- 建立统一规则模型与前后端类型边界。
- 完成列表、编辑、启停、日志筛选、应用状态和错误展示。
- 完成安装、手动升级、卸载与本软件规则清理。
- 在 Windows x64、Mac Intel、Mac Apple 芯片上记录实测结果；用户拥有 Win/Mac 设备不代表已覆盖两种 Mac 芯片或全部系统版本。

建议的源码模块为 `ui`、`desktop`、`policy-core`、`service`、`platform-windows`、`platform-macos-pf`、`pf-native`、`event-store` 和 `installers`，按单个仓库组织，不拆成多个独立项目。
