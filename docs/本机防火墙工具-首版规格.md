# 本机防火墙工具：首版规格

日期：2026-11-11

状态：需求访谈已收口；尚未编写或验证防火墙实现。下文区分用户已确认的要求、建议默认行为和待验证的平台能力。

## 1. 产品目标

开发一款可安装在 Windows 和 macOS 上的桌面软件，让用户设置“哪些来源 IP 可以访问本机的哪些端口”。

首个实际场景：电脑运行 8080 网页服务，只允许办公室指定的几台电脑访问。

首版用于用户自己和少数同事试用，接受手动安装、更新。用户具备 Windows 和 Mac 测试设备。

2026-11-11 技术选型补充：用户暂时不考虑 Apple Developer Program 账号。当前优先验证不依赖 Network Extension 签名的 macOS PF 路线，核心功能要求不因此降低；选型与验证计划另见《技术选型与验证计划》。

## 2. 已确认的范围

- 管理范围：仅本机防火墙。
- Windows 目标：Windows 10、Windows 11，x64。
- macOS 目标：macOS 13 及以上，Intel 和 Apple 芯片。
- 白名单来源：支持多个单独 IP，以及 CIDR 网段，例如 192.168.1.0/24。
- 协议：TCP、UDP，可选择两者。
- 受管端口：只有白名单中的来源可以访问，其他来源被拦截。
- 未配置端口：保持原有防火墙行为。
- 撤销权限：已有 TCP 连接和后续 UDP 通信也必须被阻断，不能只阻止新连接。
- 日志：同时提供规则管理操作日志和网络访问日志。
- 访问日志字段：来源 IP、目标端口、协议、时间、允许或拦截结果；日志保存在本机。

远程管理已由用户明确移出首版，因此此前讨论的远程配对、单管理端授权和远程修改后的 60 秒连接确认回滚不属于当前交付范围。

系统版本和芯片列表是兼容目标，不代表已经通过兼容测试。

## 3. 建议默认行为

以下是为形成可实施规格而提出的默认行为，尚未逐项获得用户确认。开发前若发现它们会改变核心体验，应重新核实。

### 3.1 规则表达与生效

- 每条规则先以一个本机端口、协议选择和一组来源地址表达。
- 多个白名单条目取并集。某个 IP 命中任意条目即属于白名单；删除它的独立条目后，如果仍被允许的网段覆盖，它仍被授权。
- 端口规则覆盖 IPv4 和 IPv6 的入站访问。若只配置 IPv4 来源，受管端口上的 IPv6 来源也不能绕过限制。
- 规则作用于其他机器访问本机的流量；本机回环访问的行为应在原型阶段明确并测试。
- 提供创建、编辑、启停和删除规则操作；停用或删除只撤除本软件对该端口施加的管理规则，回到其他现有策略决定的状态。
- 不把端口白名单中的 IP 当作设备身份。DHCP 地址变化、NAT 或代理可能改变防火墙实际看到的来源地址。

### 3.2 运行与恢复

- 安装和必要的系统配置通过管理员授权完成。
- 界面与执行防火墙操作的后台服务分离；关闭窗口后规则继续生效。
- 重启后的规则恢复、后台服务异常和更新过程中的规则状态必须验证。
- 修改前保存本软件的配置版本；应用失败时报告失败，并恢复能够安全恢复的本软件状态。
- 卸载时清理本软件拥有的规则和服务，避免误删用户或其他软件创建的配置。
- 遇到系统策略或其他安全软件冲突时，明确报告限制，不将“写入配置成功”直接显示为“实际访问验证成功”。

### 3.3 日志

- 管理日志至少覆盖规则创建、修改、启停、删除及执行结果。
- 网络日志描述过滤层的连接或访问尝试；“允许”不代表网页已成功响应。
- 除已确认字段外，建议保留来源端口、命中规则和配置版本，便于排查。
- 采用有界存储和轮转；高频事件允许汇总，并明确显示汇总或丢失情况。
- 日志采集失败应显示状态，不能用空列表表示“没有访问”。

## 4. 双平台验收场景

每项都需要记录系统版本、芯片或架构、网络环境、操作步骤和实际结果。当前尚未执行这些测试。

### A. 基本白名单

1. 在被保护电脑上启动 8080 网页服务，确认服务监听地址和基础连通性。
2. 将办公室电脑 A 的实际来源 IP 加入白名单。
3. A 可以建立新连接并访问服务；不在白名单中的电脑 B 无法访问。
4. 增加第二个来源 IP，验证两个来源都能访问。
5. 使用 CIDR 网段，验证网段内和网段外来源的结果。

### B. 已有通信撤权

1. A 在允许状态下建立持续 TCP 传输，例如大文件下载或 WebSocket 数据流。
2. 修改规则，使 A 不再命中任何白名单条目。
3. 验证新策略生效后的后续网络数据被阻断，而不是仅验证重新打开网页失败。
4. 对持续 UDP 流量重复测试；UDP 不以 TCP 式连接断开作为判据。
5. 分别记录策略提交和实际阻断时间，明确实现可达到的延迟。

### C. 协议和地址覆盖

- TCP 与 UDP 分别通过独立测试服务验证，不能用网页测试代替 UDP 测试。
- 同端口号的 TCP、UDP 选择必须与界面配置一致。
- 验证 IPv4、IPv6，以及实际使用的有线、Wi-Fi 网络接口。
- 若环境存在 VPN、Docker、虚拟机、代理或端口转发，应单独验证其网络路径；这些路径的兼容性尚未确认。

### D. 其他策略与生命周期

- 未配置端口的原有访问结果不因本软件启用而改变。
- 验证现有放行规则不会使白名单外来源绕过本软件限制。
- 验证现有拒绝策略导致白名单来源仍无法访问时，软件能正确诊断或明确提示限制。
- 验证关闭界面、重启、规则应用失败、停用规则和卸载后的状态。

### E. 日志真实性

- 白名单内访问、白名单外访问和管理操作都能与实际测试事件对应。
- 验证来源 IP、端口、协议、时间和结果的准确性。
- 验证大量重复访问下的资源占用、轮转和日志完整性提示。

## 5. 实施顺序

### 阶段一：验证系统过滤能力

先制作最小原型，在 Windows 和 macOS 上分别验证单端口白名单、撤销已有通信和访问日志。候选方向是使用系统原生过滤能力，并为两个平台分别实现适配；具体接口、规则优先级和所需权限需以官方文档和实测确定。

这一步的关键不是界面，而是三个问题：现有放行规则能否绕过限制、已经建立的通信能否按要求被阻断、允许和拦截事件能否可靠记录。

### 阶段二：规则执行与本地服务

确定规则数据模型、地址解析、配置存储、权限边界、失败恢复、后台运行和日志轮转。界面只能调用受限的规则管理接口，不应获得任意高权限命令执行能力。

### 阶段三：桌面界面

建议提供规则列表、规则编辑、访问日志、操作日志和服务状态。显示实际应用状态及错误原因，支持按来源 IP、端口、结果和时间筛选日志。

### 阶段四：内部试用包

交付对应平台安装包、手动更新说明和可重复的测试步骤，在用户具备的 Windows 与 Mac 设备上执行验收。测试记录应明确已验证的版本与架构，以及仍需补测的组合。

## 6. 当前结论

需求已经足够启动双平台技术原型。尚不能把“已有连接立即阻断”“完整访问日志”或所有目标系统兼容性视为已实现能力；必须先用实测结果确定实现方案，再制作完整试用版本。
